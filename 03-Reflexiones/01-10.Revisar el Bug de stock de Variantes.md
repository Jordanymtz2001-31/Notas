# Revisar el Bug de stock de Variantes

> [!info] ❓ **La Duda / Reflexión**
> Escribe aquí la pregunta o el pensamiento inicial de forma clara.
> 1. Revisar como colocar un mensaje de que si en un producto x todas sus variables no tiene stock(agotado), es decir que estan en 0, colocar un mensaje de Agotado.
> 2. Pero si por lo menos una variante tiene stock disponibles color el mensaje que ya esta definido **"Selecciona una variantes para visualizar el producdo"** 
> 3. Pero si hay productos de forma general sin variantes aun, entonces colocar un mensaje **"No disponible aun"** o al similiar.
> 4. Y el mas importante existe un **BUG** el cual consiste en que aquellos productos que no tienen variantes aun, toman el stock del color de la primera variante de otro producto que si tiene, esto al momento de entrar al primer modal del producto que aplique esta condicion. Por otro lado si entro primero al modal que no tiene variantes no muestra ni el mensaje definido ni el la cantidad que toma de los otros proctos.

### Conclusión / Lo que aprendí
> [!abstract] Resumen en tus propias palabras
> ## Se elimino el mostrar el producto BASE
> - Se elimino por que no tiene sentido colocar un producto que no es comprable.
> ## Cambios que se realizaron en la capa de Modelo y Vistas para mejorar el flujo.
> - Se elimino el bloque de codigo de la creacion de listas de variantes en dos metodos de las vistas y se reemplazo por una propiedad en el modelo de `Producto` llamada `variantes_data` que hace exactamente lo mismo pero mejor centralizado junto con otra propiedad para transformalos a JSON llamada `variantes_data_json` el cual ayuda a mandar el formato correcto en el frontend.
> - `json.dumps` convierte la lista de dicc a un String JSON valido, esto ayudo a eliminar una parte manual en el html de producto, lo cual es mas complicado y puede generar errores imprevistos. El metodo maneja perfecto todos los casos correctamente, esntonces solo le pasamos la propiedad del modelo productos al html ya serializado.
> 	Los metodos que se les elimino son `productos_por_categoria` y `productos_view`.
> - Ventajas de centralizar en el modelo:
>	- DRY: una definición vs duplicada en 2 vistas
>	- Single source of truth: si cambias la estructura del JSON, lo haces en un lugar
>	- Encapsulación: el modelo sabe serializarse; la vista solo pasa el objeto
>	- Reutilizable: funciona en admin, shell, tests, APIs futuras sin repetir lógica
>	- Testable: puedes testear producto.variantes_data_json aisladamente
>- Contras/Tradeoffs:
>	- Acoplamiento leve: el modelo ahora conoce la forma exacta que espera el frontend (keys sku, color, etc.). Si el frontend cambia, tocas el modelo.
>	- Carga implícita: acceder a producto.variantes_data dispara la consulta si no hubo prefetch (aunque el repo sí lo hace).
>	- Import de json en models.py: dependencia estándar, pero algunos puristas prefieren serialización fuera del modelo.
>## Cambios que se realizaron en la capa de Respository para mejorar el flujo.
>- Para el listado de variantes de un producto se filtro que solo se muestran productos que tenga variantes activas(aqui se elimino productos base).
>- Con `.distinct()` pedimos que no me repita los datos(objetos), es decir si producto tiene 3 variantes que me retorne los tres diferentes que existen, de lo contrario me los repetiria.
>- El filtrado principal del variantes activos con el segundo filtro de variantes activos de abajo es lo mismo? No
>	- `Query principal (qs.filter(variantes__activo=True))` Filtra qué productos aparecen en el catálogo (excluye productos sin variantes activas). Hace JOIN y WHERE activo=True.
>	- `Prefetch (Prefetch('variantes', queryset=VarianteProducto.objects.filter(activo=True)...))` Controla qué objetos relacionados se cargan en producto.variantes.all() al iterar en el template/JS. Sin esto, producto.variantes.all() traería todas las variantes (incluyendo inactivas), desperdiciando memoria y rompiendo la UI.
>	- filter(variantes__activo=True) = "solo productos que tienen al menos una variante activa"
>	- Prefetch(...filter(activo=True)) = "y cuando cargues sus variantes, tráeme solo las activas"
>## Eliminacion del bloque de `_safe_url` en la capa de vistas.
>- Se usaba para serializar las imagenes dependiendo el caso.
>  ```python
def _safe_url(image_field):
>
"""
Versión Python del filtro safe_url.
>
Retorna la URL de un ImageField si el archivo existe en disco, o None si
el campo está vacío o el archivo físico no existe. Evita ValueError al
acceder a .url cuando la imagen se perdió entre entornos (local vs Seenode).
>
-- SI la imagen existe --> retorna la URL de la imagen
-- SI no existe --> captura la excepción y retorna None
-- SI el campo está vacío --> retorna None
"""
>
try:
>	return image_field.url if image_field else None
except (ValueError, AttributeError):
>	return None
>```
>- Los loops de serialización desaparecieron de las vistas (se movieron al modelo).
>- Ahora la serialización ocurre en Producto.variantes_data (modelo), que replica la misma lógica inline:
>  ```python
>	try: imagen = v.imagen.url if v.imagen else None
>	except (ValueError, AttributeError): imagen = None
>```
>- **¿Es mejor?**
>	1. Sí, por cohesión: la lógica de "obtener URL segura de un ImageField" vive donde se usa (modelo que serializa sus variantes), no en un helper suelto de la vista.
>	2. Menos código global: una función menos en views.py.
>	3. Equivalente: comportamiento idéntico (captura ValueError si el archivo físico no existe en disco — típico al desplegar a producción donde media/ no se copió).
